Settling how the block closers get handled
Yes, the stack of HashMaps still works. It doesn’t care whether you’re walking nodes or tokens. Only the question of when to push and pop changes. With a flat token list you need one more piece and one rule.

The rule: fixed-shape constructs consume themselves completely

Variable use, variable definition, and links all have a fixed shape with a known terminator. When the main loop hits the opening token of one of these, hand off to a handler that reads the whole construct, including its #OIC or #MKAY, and leaves the index on the token after it.

That way, any #OIC the main loop ever sees has to be a block closer. The variable-use #OIC never reaches the loop, because its handler already swallowed it. Without this rule you’d have to guess what each #OIC belongs to.

The extra piece: a stack of open block kinds

Even then, #OIC could close a paragraph, a list, bold, and so on, and each needs a different closing tag. Some of them pop a scope and some don’t. So keep a second stack, alongside the scope stack, that records which block is open (a small enum is cleaner than strings):

Block opener (#MAEK PARAGRAF, #GIMMEH BOLD, ...): push its kind onto the block stack, emit the opening tag, and push a scope if this block type opens one.
#OIC in the main loop: pop the block stack. The kind you get back tells you which closing tag to emit and whether to pop the scope stack too.
Your parser already checked that the nesting is valid, so the two stacks should stay in sync. Still, have the code error out cleanly instead of panicking if the block stack is empty when you pop. That will catch your own bugs.

Index management

Put the token vec and the current position in your struct, and make every handler a &mut self method that moves the position forward. Two tiny helpers keep things readable: one that looks at the current token without moving, and one that returns it and moves forward. The main loop is then just while there are tokens left, match on the current one.

Keep the line number from each pair handy. Every error message should use it.

Collecting the #IHAZ value

Write one helper that collects text until it hits a given terminator token:

It starts at the current position and loops, adding each text token to a buffer.
When it hits the terminator, it steps past it and returns the buffer.
If it runs out of tokens first, it returns an error. Use the line number of the token where collection started, because the end of the file is a useless place to point at.
Shape hint:

rust
fn collect_until(&mut self, end: &str) -> Result<String, String>
The #IHAZ handler is then: step past #IHAZ, read the name, check that the next token really is #ITIZ and step past it, call the helper with "#MKAY", and insert the name and value into the top scope.

Things to decide while writing the helper:

Joining tokens: if your lexer split the value on spaces, you’ll need to put spaces back. If it kept them, joining with nothing is correct. Check what your lexer actually produces for a multi-word value before you choose.
Trimming: trim the final value once at the end, not each token.
Reuse: links use the same helper with "#MKAY". Check whether any other constructs do too.
Also check your grammar for whether a value can contain a variable use or a formatting tag. If it can’t, which is likely, the helper can treat anything that isn’t plain text as an error, and that catches malformed input for free.
